## 1. Synthesis — the facts that actually constrain the design

### 1.1 The five hard constraints

**H1 — The View Mode DOM layer is not reusable in Edit Mode, mechanically.** Every row-touching function in `src/so-columns/core.js` gates on `row.cells.length === headerCount`: `applyHidden` (`:380`), `isDataRow` used by `sortRows`/`applyFilters`/`distinctColumnValues` (`:568`, called at `:500`, `:621`, `:643`), and `applyOrder` (`:711`). **✔verified.** In Edit Mode data rows carry extra system `<td>`s with inline `display:none`, so `cells.length > headerCount` and **every one of those predicates matches zero rows**. Not speculation: it is the recorded root cause of the "headers-only CSV" defect (`save/CHECKPOINTS.md:1094`), whose predicate is the identical `cells.length !== headerCells.length` at `src/csv-export/core.js:268` **✔verified**. Worst case is `applyOrder` — the header row *does* match, so in Edit Mode it would reorder the header and no data row. `applyWidths` (`core.js:325-368`) is the one exception: it iterates header cells only, so its logic transfers (copied, not imported).

**H2 — The View Mode *storage* layer is reusable in principle, and must not be reused in practice.** `withOrder/withHidden/withWidths/withSort/withFilters` are pure string-keyed reducers; `normalizeScopeKey` accepts any string ≤200 chars (`core.js:49-56`) and `normalizeLabels` up to 100 strings ≤200 chars (`:58-69`) — so column *ids* pass validation as readily as labels **✔verified**. But `evictOverQuota` (`core.js:185-193`) **✔verified** does this when the shared `suiteMateV3ColumnOrder` item exceeds `MAX_SYNC_ITEM_BYTES = 7800`:

```js
next.orders = key in next.orders ? { [key]: next.orders[key] } : {};
```

It keeps **only the entry being written**. Put Edit Mode entries in that container and one Edit Mode save that tips the item over quota **silently deletes the user's View Mode layouts** — a View Mode data-loss regression caused without editing one View Mode file. Edit Mode roughly doubles the entries per record type (~1.5–2.5 KB per 45-column scope by inspection of the schema), so 7800 is reachable, not theoretical. Add the v3.21.1 lesson (`view-mode-architecture.md §4.5`): *a feature that bumps a shared persisted schema cannot be reverted by code revert alone — live storage is a one-way door.* **→ Edit Mode gets its own `chrome.storage.sync` key.**

**H3 — Mode separation is a route-gate, and the gate is the whole enforcement mechanism.** `src/shared/routes.js:282-295` **✔verified** — both `TRANSACTION_COLUMN_PERSONALIZATION` and `FORM_VIEWS` end in `&& !hasParam(context, "e")`. `tests/routes.test.mjs:273-276` and `:311-312` **✔verified** assert `?e=T` and `?e=F` disable them. A new capability requiring `hasParam(context,"e")` makes the two mutually exclusive *by construction* and leaves those negatives byte-identical — the strongest available proof of "View Mode untouched", for one additive `case` in a shared file. The brief permits that only if the plan flags it. **Flagged.**

**H4 — There is no CSS-order escape hatch.** Dossier §4: `order:` requires flex/grid; making `<tbody>` flex destroys column alignment; `<td>` cannot be reordered by CSS at all. Column reorder and sort are **true DOM node movement or nothing**. Hide/show and filter *do* have a display-only mechanism, and hiding is safe because NetSuite already hides its own system cells the same way (`src/internal-ids/runtime.js:167-181` **✔verified** filters cells by `cell.style.display !== "none"`).

**H5 — The DOM is a projection; the risk is survival, not corruption — and re-apply must be universal.** Now sourced (dossier §15): `machine.dataManager.getLineArray()` is the authoritative line store, `machine.buildtable()` **regenerates the entire table from it**, and NetSuite's own row lookup is `getElementById(sublistId + '_row_' + n)` — **by id, not sibling position**. NetSuite never reads our arrangement, so visual reordering/hiding/filtering cannot corrupt a commit. The cost lands on the other side: **everything we write into the table is discarded on every repaint**, including column widths. Consequence — *do not enumerate rebuild scopes; assume any interaction may regenerate the whole table, and make re-apply cheap, idempotent and self-suppressing.* Every feature from M2 onward depends on the M1 re-apply mechanism; none is "set and forget". The proven toolkit already exists in-repo: stamp-exclusion + identity early-return (`view-mode-architecture.md §7.1`), ownership attributes + `ensureX()` + the `SORTABLE_ATTRIBUTE` listener-duplication guard (`so-columns/runtime.js:1014-1017` **✔verified**), generation-guarded async evaluate, and the acceptance test that proves absence of a feedback loop: **count storage writes, not DOM operations** — one gesture = exactly one write, flat for 500 ms (`CHECKPOINTS.md:1237`), read from `tests/fixtures/chrome-stub.js` counters.

### 1.2 Secondary constraints that shape the plan

- **Column identity, in preference order** (dossier §3, §15): `td[data-field-name]` **[SOURCED]** → `^{machineId}_(?<columnId>.+?)(?<line>\d+)_fs$` on the cell's `<span id>` **[REPO]**, already implemented as `sublistColumnId` at `src/internal-ids/core.js:40-52` **✔verified** and running against live Edit Mode today → header label, **never**. Probe 6c confirms `data-field-name` on this account before it becomes primary; the `_fs` fallback needs no probe.
- **Row ids are `item_row_1`, not `itemrow1`** (dossier §15 correction). Never derive line number from sibling position.
- **The open line is a different object.** Live editors, focus owner, an attached `machineButtonRow` `<tr>` with a colspan cell, `td.uir-machine-focused-cell` with `div.listinlinefocusedrowcell` (editable) vs `…cellnoedit` (read-only), focus-only spacer cells that change the cell count, and transient. Exclusion set for reorder/sort/hide/filter; always force-revealed; every apply queues while a line is open (dossier §10).
- **Hiding needs a force-reveal rule.** `validateField` focusing a widget inside a `display:none` cell is a no-op → the line may refuse to commit with no visible error (dossier §7). Auto-reveal on `focusin` and on validation failure is mandatory. `!important` is mandatory too: display-defeats-hidden has three recorded sightings (`CHECKPOINTS.md:858`, `:972`, `:1143`).
- **Resize floor is 50 px, not 30.** NetSuite has **no `<colgroup>` and no `table-layout` rule** anywhere in its stylesheet, but `span[data-fieldtype] > input { width:100% !important; min-width:50px }` **[SOURCED]**. So `MIN_COLUMN_WIDTH = 30` (`so-columns/core.js:13` **✔verified**) is too low for Edit Mode; the floor is `max(50, widest widget offsetWidth)`. The absence of a NetSuite `table-layout` rule is favourable — we can set `table-layout: fixed` without fighting anything.
- **Machines paginate** (~25 rows; `netsuite.css` `--sln-start` cascade at 101/126/…/501). Sort and filter are **page-scoped**, and the UI must say so.
- **Ordered machines are a hard exclusion.** On `.uir-draggable-table` / `.uir-list-machine-ordered` / rows with `td.movable`, **row order is record data** **[SOURCED]**. Sorting and row-filtering must refuse outright there. This is a plain isolated-world DOM check — no privilege needed.
- **Decorate and hide with CSS; never insert or remove native nodes.** The most mature third-party NetSuite extension surveyed injects sublist line numbers via CSS `::before` and hides rows by class, deliberately avoiding structural edits (dossier §15). Column reorder is the single place this design deviates from established practice — which is precisely where Gate A sits.
- **Zero unit coverage exists for runtimes.** All 31 so-columns tests target `core.js`; `so-columns/runtime.js` has none (`view-mode-architecture.md §5.4`). Push everything testable into the new core.
- **Injected buttons must be `type="button"`.** Cosmetic in View Mode, safety-critical inside `main_form` where a bare `<button>` defaults to submit. `so-columns/runtime.js:250,456,740,952,977` **✔verified** already does this.
- **Dev loop:** one human bottleneck (extension reload + popup toggles, neither automatable) and one escape hatch (`python3 -m http.server 8931` + a self-loading fixture, no reload needed). Assert at **computed style / bounding rect**, never a class name or `.hidden` (`CHECKPOINTS.md:973`).
- **Gate arithmetic for a new module** (**✔verified** against `manifest.json:41-77`, `package.json:10`, `tests/verify.mjs:30-63`, `:156-184`, `tests/fixtures.test.mjs:101`): manifest `js`+`css` arrays and their byte-for-byte `deepEqual` mirror in `verify.mjs`; `node --check` per new file plus the new `*.test.mjs` in `package.json`; the fixture added to the `verify.mjs:156-169` link list; and — only if the fixture enters `route-catalog.js` — a baseline PNG plus a bump of `fixtures.test.mjs:101` (currently `28`). Keeping the Edit fixture out of the catalog avoids the last two.

## 2. Candidate architectures

All three assume the §1 non-negotiables: new capability requiring `hasParam("e")`, default-off + `startPaused` (so the 28 baselines cannot move), ownership-attribute-stamped nodes, synchronous cleanup, no `innerHTML`, no imports from `so-columns`.

### A — Parallel Edit Mode module family (`src/edit-grid/{core,runtime}.js`) — **RECOMMENDED**

A full sibling of `so-columns`, mirroring its shape but sharing none of its code or storage.

**Attachment + survival.** Lifecycle watcher in `mode:"continuous"` re-runs the idempotent install on every relevant mutation; a full `buildtable()` regenerate is a large `childList` mutation that cannot be missed, and the microtask flush lands before paint. Feedback loop prevented deterministically by (1) stamp exclusion — `relevant()` returns false for nodes carrying the ownership attribute; (2) identity early-return — join current column ids, compare to target, zero writes when equal. Because Add/Remove renumbers every row id and `_fs` span, **re-derive identity from `data-field-name`/`_fs` on every install; never trust a surviving `data-*` stamp on a `<td>`.** All re-apply flows through one `onMachineRepaint()` seam so adopting `postBuildTableListeners` later is a one-function change.

**Persistence.** Own key, own container `{schemaVersion:1, grids:{[scope]: entry}}`, scope key `` `${companyId}:${userId}:${type}:edit` `` from the same `session_status_init.jsp` parse (`so-columns/runtime.js:66-86` **✔verified**), entries keyed by **column id**, never label. With a separate key the `:edit` suffix is belt-and-braces — it makes a stray cross-mode read obvious for the cost of one string.

**Trade-offs.** Cost: ~1800–2100 new lines, and `planOrder`-class logic exists twice in the repo — already house doctrine (`06d9cfe` copied it into `form-views` rather than importing, because each core is vm-sandboxed alone). Benefit: strongest isolation, a genuinely revertible feature (delete the directory + 6 additive lines; `main` ignores an unknown storage key), maximum unit-test surface, and a Gate-A or Gate-B failure costs exactly one milestone.

### B — Shared column engine consumed by both modes

Extract mode-invariant logic from `src/so-columns/core.js` into `src/shared/column-engine.js`, parameterized by a per-mode column adapter; both cores consume it.

**Why it loses — three independent reasons, any one fatal:**

1. **It violates the brief's hardest rule.** `docs/BUILD-BRIEF-edit-mode.md:78-81`: *"Leave the existing View Mode implementation completely unchanged — enforce by diff: no View Mode module may be modified."* This approach's premise is modifying `src/so-columns/core.js` and, for adapter injection, `runtime.js`.
2. **It breaks the vm-sandbox test doctrine.** Cores are tested by `runInNewContext(source, sandbox)` with only the globals they legitimately need (`tests/so-columns.test.mjs:11-16` injects `{TextEncoder}` **✔verified**) — *that isolation is itself the test*. A core importing a module means loading the engine into every sandbox, rewriting all 31 so-columns tests' harness, and weakening the purity gate at `tests/so-columns.test.mjs:648`.
3. **The blast radius lands on the wrong side of the risk ledger.** It puts a refactor of 1935 shipped, live-verified lines in front of a feature whose two gates (A and B) are still unanswered. If either fails, the refactor was pure cost.

Net new code is smaller (~900–1100 lines) and long-term duplication lower — the right shape **later**, as a separate refactor once Edit Mode is stable and generalizing beyond Sales Orders is on the table (which the brief's completion section asks about). Not now.

### C — Lean variant: thin edit runtime, storage delegated to `SuiteMateV3SoColumnsCore`

No new core. One `src/edit-grid/runtime.js` (+ CSS + fixture) doing Edit-Mode DOM work inline and calling the already-global, already-frozen `SuiteMateV3SoColumnsCore.normalizeStored/with*` for persistence under an `:edit` scope key. Manifest delta 1 js + 1 css; no new schema; no new test file.

**More credible than it looks.** Reading another family's core from a *runtime* has precedent: `src/internal-ids/runtime.js:7` reads `globalThis.SuiteMateV3RecordActionsCore` **✔verified**, and manifest ordering guarantees `so-columns/core.js` (index 9) loads before any runtime appended at the end **✔verified**. "Cores must not import cores" constrains cores, not runtimes. It would be the smallest diff in the repo's history for a feature this size.

**Why it loses — two checkable defects:**

1. **Cross-mode data loss.** Sharing `suiteMateV3ColumnOrder` shares `evictOverQuota` (`core.js:185-193`): an Edit Mode write past 7800 bytes **deletes the user's View Mode layouts** (H2). A View Mode regression that would pass the brief's diff check and fail its intent. It also re-arms the v3.21.1 shared-schema one-way door.
2. **Zero automated net on the riskiest code in the project.** With no new core, *all* Edit Mode logic lives in a runtime — and runtimes have no unit tests at all in this repo. This is the highest-consequence surface SuiteMate has touched; fixture+live-only coverage inverts the risk budget.

A patched C (new key, keep the rest thin) converges on A with a thinner core — i.e. A executed well, so it is folded in rather than kept separate.

### Recommendation — **Architecture A**

1. **The only option that satisfies the brief's enforcement rule literally.** `git diff --name-only main | grep so-columns` stays empty except the one-token `FOREIGN_NODE_SELECTOR` addition, which the plan flags.
2. **The only option keeping the View Mode blast radius at zero for storage**, which C cannot (H2) and B does not attempt.
3. **It maximizes the only automated net that exists.** Logic in `core.js` is unit-testable; logic in `runtime.js` is not.
4. **It fails cheaply.** Gate A can kill one milestone (M4); Gate B can kill one milestone (M7). Everything earlier stays shipped. B makes a gate failure retroactively expensive; C makes every milestone share one untested file.
5. **It matches repo precedent** — `b774797` (smart tab titles) for adding a module family, `06d9cfe` for copying rather than importing.

**Contingency inside A (not a fourth architecture):** if Gate A fails, reuse the same module's storage + control bar for the dossier's read-only overlay **only if the owner asks** (§5 Q3). Do not build it speculatively.

## 4. Milestone ladder

Every milestone is independently shippable and ends in a **checkpoint**: `npm test` green (expect **213 + new tests**, **28 baselines at 0.000 %** — a moved baseline is a defect, not a baseline to refresh), a fixture round-trip, live evidence where applicable, a `save/CHECKPOINTS.md` entry in the house shape (`### Included` / `### Verification`), and a commit on `feature/edit-mode-table-enhancements`. Per `CHECKPOINTS.md:3` the next milestone does not begin until the previous checkpoint passes. Version stays frozen at 3.21.1 until a final owner-gated bump across `package.json:3`, `manifest.json:5`, `tests/verify.mjs:13`.

**M0 — Probe pass (~30 min, no code, no save).**
Scope: run dossier §12 probes **2, 6, 6b, 6c, 6d, 8** read-only on `id=16342809&e=T`, plus 3, 7, 9, 10, 12 if time allows. They cost almost nothing and each one changes the design of what follows: **6b decides whether sorting exists at all (Gate B)**, **8 decides the reorder milestone (Gate A)**, 6c decides column identity, 6d settles the disputed `data-machine-name`, 6 tells us whether the `postBuildTableListeners` optimization is available later.
Gates — live only, read-only DOM/console reads; probe 8 additionally opens, edits and commits a **line** (in-page only, no record save — §5 Q2). **Probe 5 is deferred:** it requires a save and is diagnostic only (U1).
Checkpoint: a probe transcript committed into the plan doc + `save/CHECKPOINTS.md`. It becomes the binding evidence behind every "supportable"/"not possible" verdict in §3. No source files change.

**M1 — Shared Edit Mode foundation.**

## 5. Open questions for the owner

Four decisions research cannot make.

**Q1 — Does Edit Mode get its own toggle, or ride the existing one?**
Options: **(a)** new opt-in flag (e.g. `salesOrderColumnsEdit`), default off — costs the settings schema 5→6 migration, the repo's highest-ripple change (`settings.js`, `settings-transfer`, popup, `verify.mjs:939-965`, four test suites). **(b)** reuse the existing `salesOrderColumns` flag — zero settings ripple, one mental model, but every existing user with the toggle on gets enhancements on a live editing surface the moment they upgrade, without consenting.
**Recommendation: (a).** The ripple is known, bounded and has a working precedent (`b774797`); silently enabling a live-edit-surface feature on existing installs is not worth saving a day. It also lets the feature be switched off independently if a live defect appears.

**Q2 — What may the M0 probe pass do on the locked record?**
Two distinct asks. **(i) Probe 8 (Gate A)** must permute two `<td>`s, then open a line, change a field and click OK. In Classic Edit Mode a line commit changes **in-page state only** — nothing reaches the server until Submit, and navigating away discards it. **(ii) Probe 5** would name the serialized payload format, but it **requires an actual save** and therefore the four-eyes gate plus your explicit first-save go-ahead.
Options: **(a)** authorize (i) with a never-save rule and teardown by navigating away; **defer (ii) entirely**. **(b)** authorize both. **(c)** read-only only — leaves Gate A unanswerable and forces column reorder to be declared not possible by default.
**Recommendation: (a).** Probe 5 is diagnostic, not load-bearing: this design never reads or writes the serialized payload, `dataManager` is the sourced authority, and probe 8 verifies commits through `nlapiGetLineItemValue`. **Deferring it means the entire plan up to M7 needs no record save at all.** *Sub-point (C7): the brief's RECORD LOCK URL is the view URL — please confirm the lock covers the same record with `&e=T` appended.*

**Q3 — If Gate A fails, what replaces column reorder?**
Options: **(a)** declare reorder not technically possible in Edit Mode, justify it in the feature-status table with the probe transcript, and ship the other four features. **(b)** build the read-only sorted/filtered/reorderable overlay as a substitute (~+500 lines, a genuinely different product — you cannot edit in the sorted view). **(c)** ship reorder anyway with an explicit corruption warning.
**Recommendation: (a).** The brief explicitly accepts "not possible" when justified; (c) risks corrupting real sales order data and is not an option I would take; (b) is a new feature deserving its own brief. Note the odds improved with the revised dossier — `buildtable()` regenerating from `dataManager` means Gate A now tests only the narrower incremental-sourcing path.

**Q4 — If Gate B passes, are page-scoped, session-only sort and filter worth shipping?**
If the SO item machine turns out to be an ordered machine, sorting and row-filtering are **off regardless of preference** — this question only applies if probe 6b clears them. Even then, machines paginate at ~25 rows, sort is not persisted, and native line numbers read wrong while sorted. Options: **(a)** ship both as M6/M7 with explicit in-UI page-scope disclosure. **(b)** ship filter only (it moves no nodes and is the safest mechanism in the dossier) and declare sort out of scope for this phase. **(c)** declare both out of scope and end the ladder at M5.
**Recommendation: (a) with a live-evidence exit** — build M6, then M7, and if M7's live pass shows any interference with commits or sourcing, close it as degraded-not-shipped rather than iterating. The ladder is ordered so abandoning M7 costs nothing already shipped.
